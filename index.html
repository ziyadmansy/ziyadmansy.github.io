About

I want automated testing to find bugs and security flaws before software ships, especially silent failures that give wrong results without crashing, and to report real problems instead of false alarms. My current work asks what knowledge AI testing agents need to find these failures, and how to tell a result is wrong when nothing crashes.

What I Want to Work On

I want to spend my Ph.D. answering one central question: How can automated testing catch bugs and security vulnerabilities before attackers exploit them or users pay for them, including silent failures that never crash, while giving developers a short list of real defects they can act on?

Creating test inputs is the easy part. The hard part is knowing what the right output should have been, known as the oracle problem. A crash makes that obvious, but the failures I care about most never crash. My results point to three directions:

  • Testing agents that know what they have not checked. My agents learned only from the cases they tested, so finding no problem could simply mean they had not reached the right case. I want agents that read the code to find what could go wrong, aim their experiments at those gaps and report what they still have not checked.
  • Finding failures when there is no expected answer. Some serious bugs do not crash the program, such as a rounded payment amount or a security protection that works on Android but not on iOS. I want to find them with differential and metamorphic testing: checking how the same input behaves across libraries, platforms and app versions.
  • Knowing when a finding is actually a bug. Many differences I found between libraries turned out to be intended behavior. I want tools that use the specification, other implementations and how the data is used to decide which differences are real bugs, especially when security or important data is at stake.

What I want to learn. Each of my studies showed a problem in one setting. In a Ph.D., I want to turn those findings into methods that hold across many programs and that developers trust. That means learning to combine fuzzing with program analysis, so testing agents can aim at the code they have not reached yet; to run experiments large enough to support general claims; and to build benchmarks that others can use to measure progress.

What I bring to a lab. Five years of building and securing production apps, a working LLM fuzzing setup and experience leading and teaching engineers. I will use that experience to help newer students design reliable experiments, as my professors helped me, and to keep turning research findings into fixes that maintainers merge.

Research Experience

Independent Researcher, LLM-Guided Software Testing

2026 – Present Three sole-authored studies, all under review (see Publications). It began with a fuzzing challenge Dr. Marcelo D'Amorim (NC State) set for about 70 prospective Ph.D. applicants; my solution passed, and I was one of about 20 invited to a Q&A session. Each study answers a question the previous one raised.
  • Can an LLM improve a fuzzer without seeing the target's code? (FORGE) I built a fuzzer in which an LLM improves its test generator using only how the target responds from outside. On cJSON, a C parser with 13K+ GitHub stars, valid inputs rose from 58% to 97%. On a second parser it failed, because that parser rejects inputs without saying why. Lesson: feedback is only as useful as what the target tells you.
  • How do you find bugs that never crash? (AST) JSON libraries in Flutter apps rarely crash; they silently change values. I compared four common ways to decode JSON in Dart and checked each decoded number against the original text. The LLM fuzzer first trailed a simple generator (2.9% vs. 22.2%); four facts about the libraries raised it to 28.8%. Lesson: what the fuzzer lacked was knowledge, not more searching. This work found silent data loss in Google's json_serializable and built_value, both now documented.
  • Can an AI agent learn that knowledge itself? (ICST) On eight JSON libraries in Dart and Kotlin, I gave the same fuzzer knowledge from three sources: written by me, read from the libraries' code, or learned by an agent through its own experiments. Knowledge written by a person worked best (30.9% of inputs exposed disagreements, vs. 1.5% with none). The experimenting agent helped where problems were common (50% to 67%) but missed rare ones and wrongly concluded the libraries agreed. Lesson: an agent only knows what its experiments reach. I also reported a JSON standards violation in JetBrains' kotlinx.serialization.
  • Open science: released all code, prompts and results with software DOIs, so every number can be rechecked; the key experiments were pre-registered before any data was collected.
