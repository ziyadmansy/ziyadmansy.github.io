The problem

Software often fails quietly. A price is rounded, a login token ends up in a log file, a record disappears. Nothing crashes, so no test notices, and a human expert has to find it later. Sometimes an attacker finds it first.

I found it, then fixed it

I traced the cause, reported it to Google with a proposed fix, then wrote the fix myself. A Google maintainer merged it the same day and called it a "great fix to a VERY nuanced problem." My testing also found silent data loss in Google's built_value, which its maintainer documented after my report. Together, the two libraries see over 18 million downloads a month.

Why this is hard. To catch it, a test has to know what the right answer should have been. Researchers call this the test oracle problem. A crash is easy to spot. A wrong number that looks normal is not. My research is about building automated tests that can tell, and that only report problems that are real, so developers are not buried in false alarms.

Why this matters now: PHP2Shell

A real example from October 2026 of a flaw that testing missed for over a decade.

PHP is the programming language behind most websites. In October 2026, two critical flaws in it, nicknamed PHP2Shell, let attackers take over web servers without logging in. The bug sat in code that only runs in a rare situation, when the server runs out of memory while reading a request.

  1. 2012

    PHP 5.4 is released. Every version from here through 8.5 carries the flaw.

  2. 2012 to 2026

    Years of testing never trigger it, because the faulty code only runs on a rare error.

  3. 2026

    Security researchers using AI models report the flaw.

  4. Oct 17, 2026

    The first attack attempts are reported, before any fix exists.

  5. Oct 21, 2026

    PHP releases emergency fixes for every supported version.

What it teaches, and how it connects to my work

Rare paths hide bugs

Tests mostly run the common paths. In my third study, an AI testing agent missed the rare failures and then told me everything was fine.

It is a race

AI helped find this flaw, and attackers were already trying to use it. The goal is to find such flaws before attackers do.

"No bugs found" is not "no bugs"

A testing tool should say clearly what it could not check, instead of declaring the software safe.

My research, step by step

Three studies, each answering a question the one before it left open. All three are sole-authored, and all code and data are public.

All three use fuzzing: a testing tool automatically creates huge numbers of unusual inputs and feeds them to a program to see what breaks. In my work, an AI model helps create those inputs.

Study 1 · FORGE 2027 · under review

Can AI write good test inputs for a program it cannot see inside?

The situation. Most fuzzers decide which inputs are worth keeping by watching which parts of the program each one runs. That requires the program's source code, and outside testers rarely have it. Even the security auditors at the fintech where I worked asked us for ours.

What I did. I let an AI model write programs that generate test inputs, and told it only how many of its inputs the target program rejected. I tested it on cJSON, a widely used program that reads JSON (13K+ GitHub stars).

Share of test inputs the program accepted (higher is better)

Starting input generator58%
AI-written generators, with feedback97%
AI-written generators, no feedback93%

A comparison I planned in advance reached 93% with no feedback at all, so most of the gain came from the AI's own generators. On a second program, the method did worse, because that program breaks the JSON standard in places and rejected inputs the AI expected to pass.

Lesson. Counting failures is not enough. The AI needs to know which inputs failed and why.

Study 2 · AST 2027 · under review

How do you catch a bug that never crashes?

What I did. I gave the same inputs to the four most common ways Dart apps read JSON and flagged every input where their results differed. If two libraries read the same text differently, at least one of them is quietly wrong.

Share of test inputs that exposed a difference (higher is better)

AI fuzzer at first2.9%
Simple generator I wrote22.2%
AI fuzzer with four short notes28.8%

At first the AI lost to a simple generator. When I gave it four short notes on how these libraries handle unusual values, it moved ahead. Along the way I found silent data loss in two Google libraries, json_serializable and built_value, and both acted on my findings: Google merged my fix to json_serializable, and built_value's maintainer documented the behavior.

Lesson. The AI did not need to search harder. It needed knowledge about the libraries.

Study 3 · ICST 2027 · under review

Can an AI agent learn that knowledge on its own?

What I did. Across eight JSON readers in Dart and Kotlin, I compared three sources of knowledge: notes I wrote, notes an AI took from reading the library code, and notes an AI learned by running its own experiments. I published the study plan before running it, so I could not adjust it to fit the results.

Dart: share of inputs that exposed a difference

No notes1.5%
Notes from reading the code11.6%
Notes I wrote30.9%

Kotlin: share of inputs that exposed a difference

No notes50%
Agent's own experiments67%

In Kotlin, where differences were common, the experimenting agent helped. In Dart, where they were rare, it usually missed them and then reported that the libraries agreed.

Lesson. An agent only learns from failures it manages to trigger. It misses the rare ones, and that gap is where I want to start my Ph.D.

What I want to work on next

The question I want to spend my Ph.D. on: how can automated testing find the bugs and security flaws that today only human experts uncover, including silent failures, without burying developers in false alarms?

My studies raised three open questions. All three come down to one thing: backing every result with evidence, whether a testing tool reports a bug or says there is none.

1. How can a tool tell a real bug from intended behavior?

Many differences I checked by hand turned out to be intended. A tool that reports all of them wastes developers' time. I want tools that learn what a library is supposed to do from its documentation and code, and back each report with a small example and the rule it breaks.

2. What quietly changes when an app updates a library?

Apps update the libraries they depend on all the time, often automatically, and assume that passing tests mean nothing broke. The silent data loss I found passed every existing test. I want to run each new version side by side with the old one and flag every input where they behave differently.

3. Can a testing tool do part of a security expert's job and say what it did not check?

A protection that works on Android can fail on iOS or on an older phone, even when both apps share the same code. I want tools that check each protection everywhere, and that report what they could not verify next to what they found.
